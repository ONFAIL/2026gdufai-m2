# 给第三方测试模型：验收「个人记账 AI 助手」前端框架

> 用法：把整个 zip 解压到一个目录，把下面「提示词正文」整段发给测试模型（Claude / GPT / DeepSeek / Gemini 均可）。
> 你的角色：**独立验收方**。不要预设它合格，也不要预设它有问题——用证据说话。

---

## 提示词正文（从下一行开始复制）

你是一名独立的前端架构验收工程师。我给你一个 Vue 3 前端框架代码包，请你**实际运行测试**后，判断它是否同时满足两件事：

1. **是否符合项目的协议/契约要求**（字段、反馈码、状态机、金额与时间口径等）；
2. **是否真的能充当前端框架**（可安装、可编译、可构建、路由与页面结构完整、核心交互可用）。

请先完整读取解压目录，尤其注意这三个位置：

```text
frontend/                      ← 被测代码（Vue 3 + TS + Vite）
依据文档/契约原文-module2-interface-v1.md   ← 接口契约原文（字段名/状态/反馈码以它为准）
依据文档/硬约束14条.md          ← 技术硬约束（审计的尺子）
依据文档/编码标准.md、ADR-0001-技术栈.md   ← 编码与技术栈约定
测试资产/                      ← 我方的测试套件与报告（仅作参考，见下方纪律）
```

### 一、验收纪律（最重要，先读）

- **必须自己动手验证**：真实安装依赖、跑 typecheck、跑 build、跑测试、运行 mock 函数断言。禁止只看代码就下「通过」结论。
- **契约原文是唯一字段口径来源**。任何字段名、反馈码、状态取值，一律对照 `依据文档/契约原文-module2-interface-v1.md`，不要按你的经验臆断「应该叫什么」。
- **`测试资产/我这边的测试报告.md` 是我的结论，不是给你的答案**。请先独立做你自己的测试，**最后**再看它，用来对照「你有没有漏测」。如果你一开始就读它，你的结论不算独立验收。
- `测试资产/*.test.ts` 是我方写的断言，你可以直接运行，也可以自己另写更严格的。**跑通别人的测试 ≠ 通过验收**，你仍要独立找问题。
- 遇到契约自身矛盾（例如同一字段两处写法不同），如实指出并说明你采用哪种口径，不要擅自「统一」。

### 二、必须执行的验证（逐项给出命令与结果）

1. **可安装**：在 `frontend/` 下安装依赖（`npm install` 或 `pnpm install`），记录包管理器、Node 版本、是否有 peer 冲突或警告。
2. **类型检查**：运行类型检查命令（看 `package.json` 的 `typecheck` 脚本），记录退出码与报错。
3. **构建**：运行 `build`，记录是否成功、产物体积、模块数。
4. **测试**：运行 `npm test`（vitest），记录通过/失败数量。
5. **契约符合度**：对照契约原文，逐项核验下面清单（能运行断言就运行，不能就用代码佐证）：
   - 反馈码集合：是否恰好 11 个，与契约 §1.5 全等（不多不少、不自造）；
   - 四种入站状态：`confirmed` / `pending_followup` / `duplicate` / `rejected` 的触发条件；
   - `duplicate`：是否按成功处理、复用 `transactionId`、不报错、反馈码正确；
   - 多轮追问：同一 key 连续缺失，是否满 3 轮永久 `rejected`，第 4 轮不再复活；
   - 金额：出站/展示用整数「分」（字段名 `...Cents`），但**入站 `records[].amount` 必须是「元」**（契约明文）；
   - 分转元的除法是否只出现在 `utils/money.ts`（其它文件出现 `cents / 100`、`/ 100`、`* 0.01` 即违规）；
   - 时间：是否一律 ISO-8601 `+08:00` / `Asia/Shanghai`，是否有 `toISOString()` 造成 Z 结尾；
   - 统计 `GET /api/stats`：`range` / `summary` / `buckets` / `meta` 结构，`buckets[].categories` 是否按类别汇总填充（不能恒为空数组）；
   - 账单 `GET /api/transactions`：游标分页（`cursor`/`nextCursor`，不是 `page`/`offset`）、`filter` 与 item 字段；
   - 类别与预算：字段结构、预设类别 ID 1–11 的色值；
   - 错误码：5 个 HTTP 错误码是否与契约一致。
6. **硬约束**：逐条核对 `硬约束14条.md`（技术栈、依赖白名单、200 行上限、`fetch` 唯一出口、无 `v-html`/`innerHTML`、无 `enum`、缺失值用 `null` 不用 `0`/`""`、CSS 走 tokens 变量、命名规范等）。
7. **框架职能**：`main.ts` / `App.vue` / 路由 / 四个 View（Capture / Transactions / Stats / Budget）/ 通用组件是否齐全、能否构成可运行的 SPA 骨架。

### 三、已知的两个「非 bug」提醒（避免误判）

- 方案用 `composables/useCategories.ts` 代替 pinia store——这是已审议通过的替代方案（不需要状态管理库），**不算违反**硬约束 3 的目录约定。
- `contract.ts` 超过 200 行是已登记的技术债（R3），本轮范围不要求修。请如实记录，但**不要把它当作阻断性 bug**。
