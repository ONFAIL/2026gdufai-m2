# 审议第三方独立验收报告

> 审议对象：第三方测试模型对 `gdufai-frontend-handoff.zip` 的独立验收报告（结论「修改后通过」，14 项发现 / 6 项 P1）。
> 审议角色：审议模型（hy4）。用契约原文 + 隔离目录 `gdufai-vue3-final` 独立实测逐条裁决，不采信任何一方的自述。
> 尺子：契约 `module2-interface-v1.md` 原文；10/12 号提示词对「本期范围」的定义；14 条硬约束。

## 一、结论

**第三方报告的事实认定准确、发现有价值，但严重度判定存在「范围错配」。**

- 它的**实测是扎实的**：14 项发现我用独立断言全部复现，无一虚报。它找到了我方 31 条测试的真实盲区——只校验「码/字段的形状与存在」，未校验「码的触发条件」与「字段取值逐字对齐」。这一点必须认。
- 但它把**模块 2 后端的完整实现职责**当成了本期前端框架的验收标准。10 号提示词第 6 行白纸黑字：「只做框架层……**不实现后端、Docker、完整业务逻辑**」；契约 §5 第 2 条也写明模块 2 实现在 `backend/` 下、由其他成员做。按这个范围，它的多数 P1（5 个反馈码零触发、时间兜底、sentAt 拒收）是**后端待办**，不是本期 bug。
- 剥掉范围错配后，**真正属本期、必须修的只剩两簇**：①第 4 轮补齐字段「复活」（违反 12 号提示词明确的 P0 收口要求）；②`contract.ts` 一批类型定义与契约原文逐字不符（硬约束 14 管辖，**我方第二轮复检漏审**）。
- 综合：**维持「修改后通过」的大方向，但把必修项从 6 项收敛到 2 簇**，其余转后端待办 / 技术债。

## 三、关键裁量说明

### 三.1 为什么 P1-1 / P1-3 / P2-10 不算本期 bug（范围错配）

证据链：

1. **10 号提示词第 6 行**：范围「只做框架层（工程配置 + 目录骨架 + 契约类型 + 基础工具 + API 封装 + mock 数据 + 通用组件 + 路由 + 四个页面骨架）。**不实现后端、Docker、完整业务逻辑**。」
2. **12 号提示词**对 `mock/import.ts` 的**唯一**硬性要求（第 35 行）：不得出现「含某关键字就阻断且退不出」的分支，必须保留「追问满 3 轮 → rejected」的收口路径。全文未出现 FUTURE_TIME / CATEGORY_KIND_MISMATCH / LOW_CONFIDENCE_CATEGORY / TIME_DEFAULTED_TO_CHAT_TIME / DIRECTION_FORCED_BY_CATEGORY / sentAt 拒收。
3. **契约 §5 第 2 条**：模块 2 实现在 `backend/` 下，由其他成员做；§0 边界表把「校验、分类、入库、追问状态机」划给模块 2（后端），前端只负责调用与展示。
4. 10 号方案 A–H 审议通过时，mock 状态机就只承诺「形状对齐 + 演示可用 + 守住 P0 死循环」，从未承诺实现全部 11 码的完整判定树。

因此这三项是「本期按范围有意裁剪」，第三方用「契约完整实现」的尺子量「前端骨架」，属于**验收标准越界**。它们应进后端待办清单，联调时由模块 2 实现。

### 三.2 为什么 P1-2 是真 bug（必须修）

12 号提示词第 35 行明确要求「追问满 3 轮 → rejected 收口」，且我上一轮复检的 B/N 项里验证过「同 key 连续缺字段 3 轮后 rejected」。但第三方证明：**若第 4 轮补齐字段，rejected 的记录会复活成 confirmed**——因为 `import.ts:92` 判 rejected 后没有把 key 记入「永久拒绝集合」，下一轮字段齐全时直接走 `confirmed` 分支。

这与 BUGS.md 记录的原始 P0 死循环是同类问题的另一面（原来是「不收口」，现在是「收口后又能打开」）。契约 §1.6「满 3 轮返回 rejected，模块 1 提示用户手动补录」意味着终态不可逆。**成立，必修。**

### 三.3 为什么类型定义不符是本期必修（我方漏审，诚实交代）

`contract.ts` 的类型定义与契约原文逐字不符，属硬约束 14 直接管辖，且**不涉及后端逻辑**：

- `TransactionSummary`：`totalExpenseCents/totalIncomeCents` ≠ 契约 `expenseCents/incomeCents`（契约 §2.3 响应示例）；
- `TransactionMeta`：`{timezone, isEmpty}` ≠ 契约 `{unit:'cent', isEmpty}`；
- `StatsBucket`：缺 `netCents`（契约 §2.2 bucket 示例含）；
- `TransactionItem.anomalyFlag`：`string | null` ≠ 契约示例 `boolean`；
- `StatsResponse.direction`：`Direction`（无 all）≠ 契约 §2.2 `all（默认）`。

**责任说明**：这些字段在我第二轮复检的 B2 项被判「✅ 通过」，当时只核对了「键名存在与结构形状」，没有逐字核对「键名拼写与取值集合」。这是继 R1 漏审之后，**我方第二次同类漏审**（验收尺子只查形状不查逐字值）。第三方这次的价值正在于此——它逼出了这个系统性盲区。

### 三.4 为什么 P2-7 维持原判（duplicate severity）

契约自身矛盾：§1.5 表格写 `DUPLICATE_RECORD = blocking`，但 §1.4 状态表写 duplicate「按成功处理，不要报错」，§4 联调清单也按成功对待。二者不可能同时满足。第三方单按 §1.5 判 ❌ 并列入待修，我**维持上一轮 R7 的判断**：这是契约缺陷，应走 `contract-change` 把 §1.5 改为 warning（与 §1.4 及实现一致），而不是改代码去迁就一个自相矛盾的表格。这条不算实现 bug。

## 四、必修项收敛清单（给 Gemini 的下一轮范围）

只做以下两类，其余一律不动：

**A 簇 — 状态机收口（1 项）**
- `mock/import.ts`：满 3 轮 rejected 的 key 记入永久集合，入口先短路，杜绝第 4 轮补齐复活。

**B 簇 — contract.ts 类型逐字对齐契约（4 项，改类型 + 同步 mock 运行值）**
- `TransactionSummary` → `{count, expenseCents, incomeCents}`，`mock/db.ts` 同步；
- `TransactionMeta` → `{unit:'cent', isEmpty}`，去掉 `timezone`；
- `StatsBucket` 补 `netCents`，`mock/stats.ts` 桶内补 `incomeCents - expenseCents`；
- `TransactionItem.anomalyFlag` → `boolean`，种子数据填 `false`；
- `direction` 类型/默认补 `all`（此项低优先，本期 View 只传 expense，可不阻塞演示）。

转出（不修）：P1-1、P1-3、P2-10 → 后端待办；P2-7 → contract-change；P3-12 → 技术债 R3；P2-9 limit 默认 → 低优先随手改。

## 五、对第三方报告的总体评价

- **优点**：真装依赖、真跑 dev server 验四路由、自己写独立断言而非照抄我方测试、最后才看我方报告——验收纪律执行到位，值得作为后续第三方验收的模板。
- **不足**：验收标准没有先与「本期范围」对齐，用完整后端契约的尺子量前端骨架，导致 P1 数量虚高（6 → 实为 1 项状态机 + 1 簇类型）。这个教训应写进未来的验收提示词：**先声明被测物的范围，再按范围选尺子**。
- **对我方的价值**：逼出了我方两轮漏审（形状核对 ≠ 逐字核对）。建议把「逐字比对字段名/默认值/取值集合」补进 11 号审议尺子和 bugtest 断言。
